The topic map

This is the hub's reason to exist. Fourteen sites is itself a retrieval problem, and an agent arriving at a network with no index reproduces the discovery failure that the agent-access report found inside a single site: it can read the map and cannot walk it. So here is the map. Every non-functional-requirement topic, with its position in one line, where the canonical material lives, and which site owns it.

This site owns the disciplines that have no other home, and the map that shows where everything else lives. Where a sibling has measured something, this site links that measurement and never restates it.

The deconfliction contract

Read this before the table, because it is what makes the table safe to rely on. A hub that duplicates its spokes produces two sources of truth, and the second one rots first.

Owned by this site

Testing — OWNS

Position: No mocks. No patches. Assert on contracts rather than implementation; real Chromium for integration tests, gated on an environment variable and skipping cleanly when it is absent; deploy via pytest, with numbered tests running top-down. It is affordable because typed objects are cheap to compose in memory, so the real thing is as easy to instantiate as a mock would be: the type system and the testing philosophy are one decision.

Where the measurements live: the sg-compute pack, linked from the testing page. Cross-link: coding.sgit.ai owns the conventions; this site owns the philosophy and the counter-evidence.

CI pipelines — OWNS

Position: the pipeline is a verifier, not a runner. Native per-arch builds, push by digest only, integration-test the pre-tag image, and only then assemble a manifest and give it a name. Machine images are baked, relaunched and re-verified before being tagged healthy. Versions auto-increment from one repository-root file.

Owner of the artefacts: sg-compute.sgit.ai. This site owns the pattern write-up.

Documentation — OWNS

Position: documentation is a truth system, not prose. The governing rule: if the reality document doesn't list it, it does not exist. Briefs are aspirations, not facts. Proposed features carry a PROPOSED label. Every page has a markdown twin. Day-indexes, debriefs classified as good-failure or bad-failure, a licence footer as a corpus rule.

Canonical: the reality system page, with the measurements linked to the sibling packs that took them.

IFD — Iterative Flow Development — OWNS

Position: the estate's named methodology. Rapid development with AI assistance while maintaining engineering rigour, centred on preserving developer flow state. The guides are versioned and written explicitly for LLMs assisting with IFD-based development. Minor versions are one team's output unit; majors are a release.

Nobody outside this estate has seen this methodology written up. It is this site's most original owned asset — see the IFD page, including the open question of whether publishing it is the right call.

Budgets and finance — OWNS the discipline, not the business

Position: three pillars. Profitability-first: until the traction and the cost lines are known, projections are made up. Pre-approve the ladder: approve the overrun positions at approval time, with the stopping point named while it is still cheap to name. Budget-on-the-step: budgets attached to workflow steps rather than to projects, so containment is structural.

Boundary: the discipline is publishable; this estate's own financial figures are not, anywhere. The page states that boundary on itself. Cross-link: token spend as an engineering problem belongs to wardley-maps.sgit.ai.

Project management — OWNS

Position: the project manager is where the register becomes work — a register per project, a net score, erosion, the missing reference class. Risk management and project management as one discipline with two vocabularies. Plus the estate's own way of working as the exhibit: briefs with acceptance criteria, same-day cross-team reviews, day-indexes, numbered asks and tasks, version-prefixed filenames, session handover guides.

The page includes the part nobody had written down: how a brief becomes work here, described as a system.

Resilience — OWNS the patterns; artefacts live in sg-compute

Position: design for the failure you had, not the one you imagine. A watchdog that exits hard through a deadlock rather than waiting politely, a two-phase health poller, halt-means-terminate, idle reconciliation, build-time guards each citing a production incident. Every resilience mechanism in this estate traces to a named incident — that is the doctrine, and it was nowhere written down.

Artefacts: sg-compute.sgit.ai. Doctrine: here.

The gap

Backups — on the list, and nobody owns it. Mentioned constantly across the corpus, with no doctrine anywhere: no written backup or recovery discipline beyond one proposal attached to a keys vault. This is an estate with irreversible publishing and frozen vaults, which is precisely where the absence costs most. The stub is published so the gap is visible, along with the open question that has to be answered first: is the vault model — versioning plus escrow — already the doctrine, unnamed?

Counter-evidence

The obvious objection to this page: is a hub site worth its drift risk? Fourteen spokes, all moving, and the hub's whole value is curation — which is the first thing to rot. The mitigations are the link-never-restate rule above and the generate-or-date rule the pre-release gate enforces. If those hold, the hub is worth it. If they do not, the fallback is this page alone, and everything else on the site is a bonus. That question is published unresolved rather than assumed away.
